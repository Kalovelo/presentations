Why Load Testing?

Unit tests check correctness of isolated components

E2E tests check behavior from the user's perspective

Load tests check performance & stability under high traffic

Some bugs only appear when multiple users hit your app at the same time

What can go wrong?

  • Race conditions; concurrent writes corrupt data
  • Resource exhaustion; connection pools, memory, file descriptors
  • Slow pages; acceptable at 1 user, unusable at 100

Beyond finding bugs

Load testing is also a communication tool

  • Expose weak spots; show exactly where the system breaks, not just guess
  • Generate proof; dashboards, metrics and failing thresholds are hard to argue with
  • Get stakeholder buy-in; turn "we should fix this someday" into "we need to fix this now"
  • Prioritize tech debt; data-driven arguments win budget and sprint time

What is k6?

  • Open-source load testing tool by Grafana Labs
  • Write tests in JavaScript
  • Runs in Go; very efficient
  • Built-in browser module (Chromium)
  • CLI-first, CI/CD friendly

The bad code

Two bugs that only surface under load

Bug 1: Race Condition

The /pay endpoint uses read-then-write


// Step 1: Read current balance
const user = await pool.query(
  "SELECT balance FROM users WHERE id = $1", [id]
);
const currentBalance = parseFloat(user.rows[0].balance);

// Step 2: Simulate async work (payment gateway)
await new Promise(resolve => setTimeout(resolve, 50));

// Step 3: Write new balance based on STALE read
const newBalance = currentBalance - amount;
await pool.query(
  "UPDATE users SET balance = $1 WHERE id = $2",
  [newBalance, id]
);

Bug 2: Pool Exhaustion


// db.js
const pool = new Pool({
  max: 2,
  connectionTimeoutMillis: 50,
});
  • Pool allows only 2 concurrent connections, timing out after 50ms
  • Each /pay holds a connection for ~50ms

k6 Concepts

  • VUs (Virtual Users); concurrent simulated users
  • Scenarios; different load patterns
  • Executors; how to schedule VUs
  • Thresholds; pass/fail criteria
  • Checks; assertions on responses

Minimal Example


import http from 'k6/http';
import { check } from 'k6';

export const options = {
  vus: 10,
  duration: '30s',
};

export default function () {
  const res = http.get('http://localhost:3000/api/users');
  check(res, {
    'status is 200': (r) => r.status === 200,
  });
}

Browser Module


import { browser } from 'k6/browser';

export const options = {
  scenarios: {
    ui: {
      executor: 'per-vu-iterations',
      vus: 5,
      iterations: 3,
      exec: 'uiTest',
      options: { browser: { type: 'chromium' } },
    },
  },
};

export async function uiTest() {
  const page = await browser.newPage();
  await page.goto('http://localhost:3001/');
  // interact with the page like a real user
  await page.close();
}

Race Condition Test


// 10 VUs x 10 iterations = 100 payments of $10
// Starting balance: $1000
// Expected final balance: $0

export async function raceCondition(data) {
  const page = await browser.newPage();
  await page.goto(`${BASE_URL}/users/${user.id}/wallet`);

  const payInput = page.locator('[data-testid="pay-amount"]');
  const payBtn = page.locator('[data-testid="pay-btn"]');

  await payInput.fill('10');
  await payBtn.click();

}

thresholds: {

}

Takeaways

  • Load tests find bugs unit tests can't
    Race conditions & resource limits only surface under concurrency
  • k6 makes it approachable
    JavaScript, browser support, great CLI output
  • Thresholds make it automatable
    Add to CI/CD; fail the build if p95 > 3s
  • Test the things that scare you
    Payments, auth, shared resources; load test them first
